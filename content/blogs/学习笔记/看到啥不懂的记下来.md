# 1. CRUD：Create, Read, Update, Delete


| 缩写 | 英文 | 中文 | 含义 | 常见 SQL | 常见 HTTP (REST API) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **C** | Create | 创建/新增 | 新建一条数据 | INSERT | POST |
| **R** | Read | 读取/查询 | 查询数据 | SELECT | GET |
| **U** | Update | 更新/修改 | 修改已有数据 | UPDATE | PUT / PATCH |
| **D** | Delete | 删除 | 删除数据 | DELETE | DELETE |

常用于数据库，任何需要管理数据的系统，比如后台管理系统、REST API、ORM、文件系统，都可以用 CRUD 来描述基本操作。

# 2. REST API
典型的REST API：
```
GET    /api/v1/users         获取用户列表
POST   /api/v1/users         创建用户
GET    /api/v1/users/1       获取 id=1 的用户
PUT    /api/v1/users/1       整体更新 id=1 的用户
PATCH  /api/v1/users/1       部分更新 id=1 的用户
DELETE /api/v1/users/1       删除 id=1 的用户
```
如果我有 POST、PATCH、GET、DELETE 等一整套接口，按资源来设计，那就是典型的 REST API。 如果只是暴露了一堆 HTTP 方法可调用的接口，那更宽泛地叫 HTTP API，严格说要看是否符合 REST 风格。

所以说之前我们实习的项目，介于REST API和HTTP API之间吧，风格的话也是有点像。

# 3. 菲茨定律

核心定义

该定律用于预测一个人快速移动到目标区域所需的时间。简单来说：移动时间取决于目标的“距离”和目标的“大小”。

数学公式（香农公式）

$T = a + blog_2 (\frac{D}{W}  + 1)$

• T：到达目标所需的总时间（移动时间）。
• a, b：与具体人体器官或操作设备相关的经验常数（由实验测得）。
• D：起点到目标中心的距离（Distance）。
• W：目标在移动方向上的宽度（Width）。

常见的实验就是两个方块，在不同的位置，先点一个，再点另一个，都点完后，会重新刷新在随机位置

有两个用途吧：
- 一个就是用来测试人的手眼协调度，所以可能用于健康检测，或者是FPS天赋测试这种地方
- 另一个就是界面设计，简单来说就是button的大小以及界面的交互，不能花太多时间，同时界面边缘的情况也需要考虑

# 4. CMS

## CMS是什么

**CMS = Content Management System（内容管理系统）**

一句话解释：它是一种让你**不写代码也能管理网站内容**的软件。

CMS 就像一个**自动整理的图书馆管理员**：

- 你把文章、图片、视频（内容）交给它
- 它负责存到哪里、怎么排版、什么时候显示
- 你只需要专注「写什么」，不用管「怎么放」

## 为什么到处都能看到

因为**现在大半个互联网都跑在 CMS 上**：

| 你看到的地方 | 背后可能就是 |
| --- | --- |
| 各类博客、企业官网 | WordPress（占全球网站约 40%+） |
| 新闻门户 | Drupal、Joomla |
| 商城、店铺后台 | Shopify、Magento |
| 公司内部文档站 | Confluence、Notion（广义上也算） |
| 国内的很多网站 | 织梦、帝国 CMS |

原因很简单：**从零手写一个网站的登录、发文、评论、权限管理，成本太高了**。CMS 把这些通用功能打包好，普通编辑点几下按钮就能发布内容——就像没有人为了吃面包先去种小麦一样。

然后博客的流程其实就是一个比较简单的CMS模型

经典 CMS 的定义包含四个职能，你的博客把它们分配给了不同的工具：

| CMS 职能 | WordPress 里谁负责 | 你的博客里谁负责 |
| --- | --- | --- |
| 内容存储 | 数据库（MySQL） | Git 仓库（一堆 .md 文件） |
| 编辑界面 | 网页后台 | 本地编辑器（VS Code / Obsidian） |
| 发布流程 | 点「发布」按钮 | push 触发 CI |
| 排版渲染 | 服务器运行时实时渲染 | 构建时一次性生成静态 HTML |

所以说「模板」只是其中的**展示层**——它相当于 WordPress 里的主题，真正干活的是整条管线。

## 那它到底算不算 CMS？

**严格派会说不算**，因为缺了 CMS 最核心的东西：

- **运行时管理**——文章不是存在系统里被动态调用，而是编译成死文件。想改一个错别字也要重新走一遍构建。
- **图形后台**——它默认使用者会写 Markdown、会用 Git。如果想让不懂技术的人投稿，这条流水线立刻失灵。
- **媒体库、定时发布、草稿审核**这些「管理」功能，全靠你自己想办法（或者没有）。

**宽泛派会说算**，因为 CMS 的本质诉求——「内容和展示分离，写的人不用管代码」——你确实完整实现了，而且实现得比 WordPress 更干净：每篇文章就是一个纯文本文件，永生（Markdown 五十年后也能读，MySQL 转储文件可不好说）。

# 5. 哈希表
就是两数之和问题，比较好的解决方案
```python
def twoSum(nums, target):
    seen = {}                      # 值 -> 下标
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:           # 一次查询,不是一遍遍历
            return [seen[need], i]
        seen[x] = i                # 先查再存,天然避免用自己
    return []
```
然后其中enumerate函数的参数是这样的，就是传一个序列进去，然后从头开始枚举
```python
enumerate(sequence, [start=0])
```

# 6. LoRA(Low-Rank Adaptation of Large Language Models)
LoRA（Low-Rank Adaptation） = 冻结大模型原来的权重，只在旁边挂两个「小纸条」来学新东西。它是参数高效微调（PEFT）里最出名的一种。

## 总览
形式    W' = W + (α/r)·B·A,  A~N(0,σ²), B=0
省钱    参数 1/10000 · 显存 1/3 · 速度 +25%
延迟    合并后 = 0（by construction，不随 batch/序列变）
代价    合并后无法单 batch 多任务

## 超参
挂哪    Wq + Wv 起手；预算固定就"多挂层+小 r"
r       1~16 都行，GPT-3 上 r=1 就够；换语言/换领域 → 加大到接近 d
α       α = 2r 起手，实质是 (α/r) 缩放，改 r 时不用重调 lr
lr      1e-4 ~ 5e-4（GPT-3 用 2e-4）

## 原理
① ΔW 是低秩的（top-1 方向在 r=8/r=64 之间重叠 >0.5）
② ΔW 不复制 W 的主方向，而是放大 W 里被忽略的"任务特定方向"
③ r=4 时放大倍数 ~21×；r=64 只剩 2× → 多出来的维度是噪声

## 何时使用
· 下游是全新语言/全新模态 → 需要 r≈d，不如直接全量微调
· 要一个 batch 混跑多个任务 → 得放弃 merge（有延迟）
· 低数据（100 条）→ 反而该用 LoRA（63.8 > FT 60.2），但绝不用 prefix

# 7. QLoRA
简单说，就是LoRA的量化版本

## QLoRA 三段式
存 4bit（NF4）  →  算 16bit（BF16）  →  只更 LoRA（BF16）
显存大头是「底座权重」和「激活梯度」，不是 LoRA 参数
    7B: 底座 5048MB | 参数 26MB | 输入梯度 567MB(→18MB w/ ckpt)

## 三个技巧
NF4   正态分布分位数量化 + 非对称零点，比 FP4 好 ~1 点
DQ    量化常数再量化 32→8bit，0.5 → 0.127 bit/param，65B 省 3GB
Paged 优化器状态换出到 CPU，防长序列 OOM（bs=16 时同速）

## 照着抄的超参
r=64, α=16, 全线性层, dropout 0.1(≤13B)/0.05(≥33B)
lr 2e-4(7/13B) → 1e-4(33/65B), batch 16 → 32 → 64, 步数 1e4 → 5e3 → 2.5e3
constant lr, group-by-length, max_grad_norm 0.3, Adam β2=0.999

## 最值钱的两句话
① 量化掉的精度，能被 adapter 训练「补回来」（Table 3/4）
② 数据质量 >> 数据量：9千条 OASST1 打赢 45万条 FLANv2
   （数据量翻3倍只涨 0~0.5 点，换数据集差 1.5~8 点）

# 8. 压缩三件套（量化、蒸馏、剪枝）

## 总览

| | 蒸馏 | 量化 | 剪枝 |
|---|---|---|---|
| **改什么** | 换个小模型 | 参数{换精度} | 删参数 |
| **省什么** | **算力、显存、延迟** | **显存、带宽** | 显存（结构化才省算力） |
| **掉点风险** | 中（学生能力上限） | 低（8bit 几乎无损） | **高** |
| **要重训吗** | ✅ 必须 | ❌ PTQ 不用 | 结构化要 |
| **工业界采用率** | 中 | **最高** | 低 |

---

## 一、量化：性价比最高，先做这个

**核心机制**：把 FP16 权重压成 INT8/INT4，用缩放因子（scale）加零点映射回数值范围。

```
W_fp16  →  W_int  = round(W / s) + z  →  推理时 W = (W_int - z) × s
```

**关键事实**：decode 阶段是**显存带宽瓶颈**（每生成 1 个 token 都要读取一遍全部权重），因此**减少要搬运的字节数，就最直接地降低延迟**喵。

| 位宽 | 效果 | 典型方案 |
|---|---|---|
| INT8 | 近乎无损，显存减半 | LLM.int8()、SmoothQuant |
| **INT4** | 主流最优选择，显存约 1/4 | **AWQ、GPTQ**、GGUF(Q4_K_M) |
| FP8 | 新卡原生，几乎无损且能提速 | H100/L40S |

**两个必须特别注意的问题**：
- 难点在于**激活离群值**：SmoothQuant 把离群值从激活迁移到权重上，才使 W8A8 方案可用。
- **4bit 下数学、代码、长尾语言掉点最明显**；但**量化后用 LoRA 微调，可以把损失补回来**。

> 一句话：**只压权重最安全，同时压 KV Cache 收益更大但更敏感。**

---

## 二、蒸馏：唯一能真正缩小模型的方案

**核心机制**：小模型（学生）不只看标准答案，还学大模型（老师）的**完整输出分布**。

```
L = (1-α)·CE(y, p_s) + α·T²·KL(p_t^T ‖ p_s^T)
                          ↑ 温度 T 放大"暗知识"（类间相似度）
```

**三档信息量**（效果递减）：

| 学生能看到 | 效果 | 成本 |
|---|---|---|
| 老师的 **logits**（白盒） | 最好 | 需老师权重 |
| 老师生成的**文本**（SeqKD/黑盒） | 一般，但通用 | 只要 API |
| 老师的中间层特征 | 更好但要对齐结构 | 最贵 |

**生成任务要注意**：经典 KD 是 forward KL，学生容易「摊大饼」；**改用 reverse KL 或 on-policy GKD**（学生自己采样，老师打分）效果更好。

**关键约束**：**学生容量有上限**。7B→1.5B 可行，7B→0.5B 会丢失推理能力。

> 一句话：**蒸馏能减少模型规模，是唯一能真正改变推理开销上限的压缩手段。**

---

## 三、剪枝：听起来美好，实际上难做

**核心矛盾**：

```
非结构化剪枝（删单个权重）
  → 稀疏矩阵 GPU 跑不快，只是"省显存"，几乎不提速
  → 所以 SparseGPT / Wanda 实际用的人少

结构化剪枝（删整个 head / channel / layer）
  → 真提速，模型真的变小
  → 但必须重训恢复精度，成本高
```

| 类型 | 加速 | 备注 |
|---|---|---|
| 非结构化（Magnitude/Wanda） | ❌ | 需要专用稀疏 kernel |
| **2:4 结构化稀疏** | ✅ 理论 2x | Ampere+ 硬件支持 |
| 结构化（层、头、通道） | ✅ | **主流路线** |

> 一句话：**不重新训练就没有加速效果；要加速必须做结构化剪枝并重新训练。**

---

## 四、三者关系（关键认知）

```
蒸馏  →  得到"本来就小"的模型      ← 改变能力上限
量化  →  让模型"占得少、搬得快"    ← 不改结构
剪枝  →  让模型"真的少几块肉"      ← 改了结构，但要重训

最佳实践：先蒸馏出小模型 → 再量化部署 → 剪枝只在极端场景用
```

**为什么量化用得最多**：
- 不需要重新训练（PTQ）
- 没有架构门槛
- 掉点是**可控且可修复**的（后接 LoRA）
- 直接命中 decode 的带宽瓶颈

---

## 五、五句话收尾

1. **蒸馏改能力上限，量化改存储开销，剪枝改结构。**
2. **decode 是带宽瓶颈，量化最对症。**
3. **非结构化剪枝没有实际加速效果**，这是它最大的问题。
4. **量化掉点可以用 LoRA 补回，蒸馏掉点补不回**，因为学生根本没有那个容量。
5. **顺序**：先蒸馏出小模型，再量化，最后才考虑剪枝。

# 9. k8s
之前一直看见有人提，k8s全称kubernetes，然后与docker的区别主要是在docker 负责把应用及其依赖打包成镜像，并在单台机器上运行；K8s 负责把一堆这样的镜像调度、编排到整个集群上运行。

## 一、K8s 是什么

K8s（Kubernetes）是一个**容器编排平台**喵。它的工作对象是“我要 20 个副本一直运行着，服务暴露在 80 端口，滚动更新不中断”，并不直接关心单个容器怎么运行喵。

它负责的关键能力包括：
- **调度**：把一个 Pod 放到哪台机器上由调度器决定，同时考虑资源余量和亲和性
- **自愈**：容器崩溃或进程失活就重启；节点失联就把它上面的 Pod 迁移到别处
- **弹性伸缩**：HPA 根据 CPU 或自定义指标增减副本数
- **服务发现与负载均衡**：Service 提供稳定的虚拟 IP 和 DNS 名，把流量分发给后端的 Pod，Pod 更换 IP 也不影响
- **滚动更新与回滚**：Deployment 支持一边启动新的 Pod，一边关停旧的 Pod；出问题可以 `rollout undo` 回到上一个版本
- **配置与密钥**：ConfigMap 和 Secret 让配置与镜像解耦
- **存储编排**：PV 和 PVC 把云盘或 NFS 挂载进容器

核心对象中，你日常主要接触这几个：**Pod**（最小调度单元，一个或多个共享网络的容器）、**Deployment**（管理无状态副本）、**StatefulSet**（有状态、有稳定标识）、**Service**、**Ingress**、**Job/CronJob** 。

## 二、与 Docker 的区别

| 维度 | Docker | Kubernetes |
|---|---|---|
| 定位 | 容器**引擎与工具链** | 容器**编排平台** |
| 管理范围 | 单机上的容器 | 跨多台机器的集群 |
| 最小单位 | Container | Pod（可含多个容器） |
| 网络 | docker network（bridge、host、overlay） | CNI 插件（Calico、Cilium）和 Service 虚拟 IP |
| 故障处理 | 有 `--restart` 策略，能力有限 | 声明式自愈，持续将实际状态调整为期望状态 |
| 扩缩容 | 手动或自行写脚本 | 声明副本数或自动 HPA |
| 发布方式 | 手写 `docker run` 命令或使用 Compose | Deployment 滚动更新、灰度发布、回滚 |
| 状态管理 | 以命令式为主（`docker run`） | 以声明式为主（YAML 描述期望状态） |
| 适用场景 | 本地开发、单机部署、小型服务 | 多节点生产集群、高可用、大规模服务 |


## 三、两者的协作关系

```text
Docker/Buildah      →  构建镜像（OCI image）
containerd/CRI-O    →  在节点上运行容器（CRI 接口）
Kubernetes          →  调度、编排、扩缩容、发布
```

在本地开发中，常见组合是：**Docker Compose 启动本地环境并完成镜像构建，再推送到镜像仓库，K8s 拉取该镜像进行部署**。如果本地要模拟集群，可以用 kind 或 minikube。

## 四、选择建议

- 只需要在一台机器上部署多个服务，并且团队规模小：**先用 Docker Compose 就足够了**，别让 K8s 额外增加复杂度
- 需要多节点、高可用、自动扩缩容和滚动发布：**使用 K8s**（或者托管服务如 EKS、GKE、ACK，自建控制面的运维成本很高）
- 想在 k8s 上继续使用 Docker 的习惯：开启命令别名或使用 `nerdctl`，但生产环境不建议在节点上再安装 docker daemon
